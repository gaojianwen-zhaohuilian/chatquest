# ChatQuest

> 多平台即时通讯消息智能抽取与日程提醒系统
>
> 通过适配器模式对接钉钉、QQ、企业微信、微信四类 IM 通道，利用大模型完成聊天文本的结构化任务抽取与相对时间归一化，并实现三级延迟提醒。

---

## 一、项目定位

大厂（钉钉 AI 小钉、飞书智能伙伴、Motion、Reclaim）已经提供了同类功能。本项目的价值不在功能列表，而在于解决大厂**不需要**面对的跨平台工程问题：

| 真实难题 | 大厂为何不面对 | 本项目的展示点 |
|---|---|---|
| 三平台三套异构消息协议 | 只服务自己平台 | 适配器模式 + 统一抽象 |
| 主动推送能力不对称 | 平台内能力统一 | 能力探测 + 降级策略 |
| 合规边界约束 | 本身即平台方 | 工程取舍判断力 |

**一句话**：这是一个跨平台工程能力的训练与展示项目，不是产品。

---

## 二、平台能力限制表

> ⚠️ 这张表是全项目架构决策的依据。**各平台能力不对称，是核心设计的出发点。**

| 平台 | 接入协议 | 读群消息 | 读私聊 | 主动推送 | 交互卡片 | 需公网地址 | 资质要求 |
|---|---|---|---|---|---|---|---|
| 钉钉 | Stream (WSS 长连接) | 仅被 @ 时 | 支持 | 支持 | 完整 | 否 | 需企业管理员审批 |
| QQ | WebSocket (botgo) | 需申请审核 | 支持 | 有频控 | 有限 | 否 | 个人实名认证 |
| 企业微信 | WebSocket | 需申请 | 支持 | 支持 | 完整 | 否 | 需企业管理员 |
| 微信 iLink | HTTP 轮询 | ❌ 不支持 | 支持 | 仅 24h 内 | ❌ 不支持 | 否 | 扫码授权 |

### 关键观察

**微信 iLink 是唯一的能力短板通道**：不支持群聊、不能主动发起（`context_token` 24 小时过期）、无交互卡片。

这直接决定了本项目必须有**能力降级机制**——不能写成 `if (platform == "WECHAT")` 的分支堆砌。

## 四、技术选型理由

| 技术 | 选择理由 |
|---|---|
| Spring Boot 3.x + Java 17/21 | 主攻 Java 后端；虚拟线程适合 IM 长连接的 IO 密集场景 |
| WebSocket 原生客户端 | 钉钉 Stream 与 QQ 本质都是 WS 长连接，不引 Netty 避免过度设计 |
| Spring AI + 结构化输出 | Java 原生 AI 生态；时间戳注入 Prompt 做相对时间归一化 |
| MySQL | 任务持久化，给 `confidence` / `source_msg_id` 预留字段 |
| Redis 幂等 | `platform + msgId` 作键，IM 场景下内存操作比 DB 唯一索引更快 |
| Redis ZSet 延迟队列 | 替代 Quartz；score 存触发时间戳，逻辑完全可见可调试 |

### 明确不做的事

- ❌ 前端界面（命令行 + 日志验证）
- ❌ 用户系统（单用户即可）
- ❌ 移动端 / Docker 部署（Stream 模式不需公网地址）
- ❌ 微服务拆分（单体足够，拆了是负分）

## 六、为什么不选 WeChatFerry

**明确排除的方案：微信 Hook / 协议方案**

1. **合规风险**：微信 2025 年官方公告明确将「外挂类工具」「违规获取聊天记录」列为重点打击对象，封号风险真实存在。
2. **维护成本不可控**：WeChatFerry 依赖 Windows DLL 注入，版本锁死在微信 PC `3.9.12.x`。微信 4.x 架构重写后没有稳定 hook 方案，微信自动更新即失效。
3. **协议方案非法**：模拟登录协议方案市场报价约 4000 元/账号/年，且属违规服务。

**最终选择**：官方 iLink Bot 协议，主动放弃功能完整性（无群聊、无主动推送）换取合规性与可持续性。

> 若作为商业产品，微信通道应放弃；本项目为个人技术项目，iLink 的非公开性质风险可接受。
